# 为什么这个站点不能部署到 GitHub Pages

> 结论先说：**GitHub Pages 是纯静态文件托管 —— 它只把文件发给你，不运行任何程序。**
> 而这个站点的"内容"是 20 个接口 + 一个 SQLite 数据库 + 一千多个上传文件，
> 全部需要一个常驻的 Node 进程。把 `dist/` 放上 Pages，打开会是登录页，
> 然后**永久卡在登录**：`POST https://<你>.github.io/api/auth/login` 只会得到 404。

---

## 一、硬冲突：这些能力在 Pages 上不存在

| 站点功能 | 实际依赖 | GitHub Pages |
|---|---|---|
| 登录 / 注册 / 退出 / 改密 | `POST /api/auth/*`：scrypt 校验 + `sessions` 表 | ❌ 没有服务端 |
| 课程 / 成绩 / 笔记 / 待办 / 灵感 / 日历 / 书签 / 热力图 | SQLite：`server/data/vault.db` | ❌ 没有数据库 |
| 上传与下载文件（本机实测 1500+ 个，支持 Range 断点） | 后端落盘 `server/data/files/`，并做归属校验 | ❌ 没有持久磁盘 |
| 课程 / 课表导入（成绩 xlsx、课表 xlsx、WakeUp 备份、ICS 日历） | 解 zip、解析表格、去重、写库，**全在 Node 里** | ❌ 没有运行环境 |
| 油猴脚本导入学校教务系统 | 脚本从 `*.cuc.edu.cn` 页面 POST 到后端 `/api/import/*` | ❌ 没有收请求的进程 |
| GitHub 仓库页 | 后端代理请求（为了不在前端暴露 token） | ❌ 没有代理 |
| 学习热力图 | 库里的事件流水按天聚合 | ❌ 没有查询层 |

前端实际调用了 **20 个不同的接口路径**（`/auth/login`、`/files`、`/courses`、`/import/timetable-xlsx`…），
分布在 **39 处调用点**。这些路径在 Pages 上全部 404。

---

## 二、三道即便"页面能打开"也过不去的前提

### 1. 前端写的是**相对路径** `/api`

```ts
// src/lib/api.ts L32
const BASE = '/api'
```

部署到 Pages 后它会解析成 `https://<你>.github.io/api/...`，
而 Pages 对这个路径只会回答"没有这个文件"。

### 2. 会话靠 httpOnly cookie + 每标签页令牌

`server/src/lib/auth.ts` 的 `setSessionCookie()` 下发 `HttpOnly; SameSite=Lax`（HTTPS 下再加 `Secure`），
前端把它同时存进 `sessionStorage` 以支持"一个浏览器登两个账号"。
**cookie 必须由服务端下发、每个请求都要服务端校验** —— 静态托管做不到。

### 3. 仓库里没有、也不该有数据

`.gitignore` 排除了：

```
server/data/     数据库 + 全部上传文件
.tmp/            数据库备份
docs/screenshots/ 开发截图
```

也就是说 Pages 拿到的是一个**没有数据的空壳**：能渲染登录页，但没有任何课程、成绩、笔记。

---

## 三、"混合方案"行不行？（Pages 放前端 + 后端在别处）

理论可行，但要改三处代码，并且承担跨域的代价：

| 要改什么 | 现在是什么 | 改成什么 |
|---|---|---|
| 接口地址 | `const BASE = '/api'`（同源） | 构建时注入的绝对地址，如 `https://api.example.com/api` |
| CORS 白名单 | 只放行 `localhost` 与 `*.cuc.edu.cn`（`server/src/index.ts` L65–66） | 再加 `https://<你>.github.io` |
| 跨站 cookie | `SameSite=Lax`（跨站不发送） | `SameSite=None; Secure`，否则"新标签页继承会话"失效 |

代价：多一次预检、更慢、失败点更多；而它**唯一的好处**只是省掉"后端托管静态文件"这一件事 ——
可这件事已经零配置做好了：`server/src/index.ts` L146–150 会直接托管 `dist/`，
一条 `node src/index.ts` 同时提供网页和接口。

**所以：不推荐。**

---

## 四、GitHub Pages 自身的两个额外限制

1. **免费账号的 Pages 只能从公开仓库发布**（私有仓库要付费）——这个仓库里是个人学习数据
   的代码，即使已脱敏，也不适合为了托管而必须公开。
2. Pages **不提供**自定义服务端逻辑、环境变量、持久磁盘、定时任务 ——
   恰好是这个站点需要的四样。

---

## 五、那正确的上线方式

| 方式 | 做法 | 代价 |
|---|---|---|
| **反向隧道**（推荐，已在仓库里做好） | 双击 `上线启动.bat`：后端托管构建好的网页 + 开 Cloudflare 隧道，得到 https 网址 | 需要一台常开的机器 |
| **云服务器** | 同上，但跑在服务器上 | 要选**有持久磁盘**的（容器平台的临时盘重启即丢数据） |

详细步骤见 [`上线部署.md`](../上线部署.md)。

---

## 六、如果只是想要"一个能发人的链接"

- **给同学看界面**：做一个**脱敏静态演示版**（假数据、不带任何真实课程/成绩）推 Pages —— 可以，但只能看不能登录。
- **自己真用**：用上面的隧道方案，它给你的本来就是一个能发人的 https 网址。

---

## 附：本仓库为"能部署"做过的准备（以及为什么仍不够）

- ✅ 后端已能同时托管 `dist/`（`server/src/index.ts` L146–150），所以**部署只需一个进程**
- ✅ 前端用相对 `/api`，同源部署不需要改任何前端代码
- ✅ 生产/上线有安全守卫（`server/src/lib/deploy.ts`：密码没改、注册没关就拒绝启动）
- ❌ 但**没有任何 `.github/workflows`**：本仓库从未配置过 Pages 发布，也不需要 ——
  因为它不是静态站点
